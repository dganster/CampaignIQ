# Deployment application composition

`DeploymentApplication(input_store, publication_store, preference_store, publication_enabled=False)` composes the independently verified deployment backends for the existing account application screens. All three services must be exact `PostgresAccountDirectory` instances with the same reviewed hostname, port, database, registry, issuer and immutable legacy owner mapping, and three distinct database role names. Construction performs no connection, configuration discovery, initialization, bootstrap, grant or migration. Every operation retains its underlying current-session, target, role, schema and source checks.

The input store supplies directory administration, authorized account choices, source uploads, read-only previews/reconciliation and canonical report snapshots. The publication store is used only by the append-only publisher. The preference store supplies personal display choices. Presentation adapters translate the existing input-account summary contract without changing storage routing. They do not expose a storage initialization path: schema verification is mandatory and any drift blocks access. Original legacy namespace bindings and published financial records remain read-only.

Publication availability is an explicit server setting, disabled by default. Enabling it is necessary but insufficient: the user must also confirm the specific selected account and reporting month. The current source revision, original documents, broker identity, closing inventory, permissions and predecessor are checked by the same publisher. Neither a browser checkbox nor a display-mode flag can enable a disabled service. Uploads, results and comparisons always dispatch to the deployment service; local preview publication APIs are never a fallback.

`render_application(st, application)` injects the service into the existing account dashboard, retaining private report-module instances, user/account-scoped widget state and verified original-document staging. The shared screens have an explicit deployment presentation mode with neutral application wording and account/month publication confirmation. Existing local previews retain their original default mode and behavior. Legacy inventory/results and administration retain their normal permission checks. Missing deployment storage offers no initialization button. There is no new production entry point or automatic runtime selection in this increment.

`account_runtime_roles_admin --development-only --application-integration` runs the existing independent committed-publication checks and an additional application lifecycle on the fixed disposable local clone. Three temporary restricted NOLOGIN roles are reviewed; the application creates a new synthetic account, binds and uploads four matching sources, previews/reconciles, verifies both publication gates, commits a 110-share month through the designated publisher, reads it through the dashboard/results/comparison services, and saves separate preferences. It checks VIEW sharing, archived history, revocation, disabled users, all retained owners' original inventory/results/dashboard routes, and unchanged financial rows during reads/preferences/sharing. Exact clone and role identities and unchanged copied old source tables remain prerequisites for cleanup. No forced removal or cascading cleanup is used.

The import test runs with `-I -S` against only the source/driver bundle. UI behavior is covered by Streamlit AppTests, including account state isolation and publication controls. Actual PostgreSQL verification runs on the user's machine; skipped opt-in tests are not treated as successful database verification.

The running local preview and deployed application are not switched by the installer or rehearsal. Existing saved preferences and financial records are not migrated or copied. Reviewed deployment configuration, legacy preference carry-forward where needed, backup/recovery and explicit production activation remain release tasks.
