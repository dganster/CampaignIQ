# Deployment personal preferences

`DeploymentAccountPreferences` persists supported display choices in the existing version 1 `campaigniq_accounts.account_preferences` table. It requires an explicitly configured `PostgresAccountDirectory` backed by a separately reviewed preference role. This increment supplies backend APIs and a disposable local rehearsal; it does not activate a deployed service, change the running local UI, bootstrap identities, or copy preferences from development or legacy storage.

Keys are the immutable registry, current server-authenticated user, and authorized account IDs. Administrators receive no implicit access to another owner's account. VIEW grantees can save their own choices, including for archived accounts. Disabled users and revoked grants are rejected. Saves hold the directory SHARE lock until commit, acquire a per-key transaction advisory lock, verify checksummed existing values, and require an explicit current revision. Two first saves cannot overwrite each other. Invalid or corrupt rows block saves; there is no automatic repair. Verification errors and caught SQL failures roll back the whole transaction. Loads use read-only repeatable snapshots. There is no initialize method or startup DDL.

Version 4 adds only reviewed grants for a distinct existing preference role. Versions 1–3 retain their original source checksums and policies. The preference role can SELECT/INSERT/UPDATE personal choices but cannot mutate financial artifacts, source drafts, originals, retained public storage, or delete preferences. Input and publication roles retain no preference privileges. Existing metadata permissions are retained for the guarded directory connection, including SHARE locks; application account authorization remains mandatory. Plans pin role OID, target database, policy, effective table/column privileges, and catalog fingerprint. No role creation, passwords, ownership changes, PUBLIC grants, revocation, or default privilege changes occur in migration APIs. The caller owns the transaction and must propagate errors.

The `--personal-preferences` administrator rehearsal extends the already verified committed-publication runner. It uses a disposable clone of the fixed local restore, three generated NOLOGIN roles, and only synthetic new account preferences and metadata. Grant rollback, exact repeat, committed independent persistence, stale revision, owner/account/user isolation, concurrent first save, VIEW/archive handling, active-save revocation, disabled access, injected verification and caught SQL errors, corrupt-row rejection, and actual SQL role denials are checked. It independently verifies copied originals, financial records, previous preference tables and the retained restore. Exact created database/role OIDs and unchanged copied source rows are prerequisites for cleanup; there is no forced database removal or cascading cleanup. Receipts remain in the normal user's records folder.

Existing personal preferences remain unchanged. Explicit carry-forward of any retained legacy preferences, deployment service composition, identity mapping review, backup/recovery and production activation remain separate work before release. No production access is authorized by running this local rehearsal.
