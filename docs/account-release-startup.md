# Reviewed account release startup and offline packet

The new `ui/account_deployment_entrypoint.py` is a separate, unactivated entry point. It does not replace the existing Render start command or the local signed-in preview. It reads only the new `CAMPAIGNIQ_ACCOUNT_RELEASE_FILE` and `CAMPAIGNIQ_ACCOUNT_RELEASE_SHA256` configuration contract and three fixed role-specific DSN variables. It never falls back to `CAMPAIGNIQ_DEV_DATABASE_URL`, local development schemas, a filesystem runtime or a synthetic registry.

The private release JSON contains a version-4 schema requirement, registry/issuer/complete immutable legacy ownership mapping, one exact database endpoint, three distinct reviewed role names, the full Python source-file inventory, public OIDC client/metadata/callback settings, and an explicit publication availability boolean. It contains no database password, OAuth client secret or cookie secret. Duplicate/unknown fields, malformed routing, unsupported versions, unexpected files, invalid source digests, mismatched roles, alternate issuer metadata, and HTTP callbacks are rejected. `release_document` builds proposals from explicit trusted backend settings, role targets and public auth settings. A separate review of the canonical configuration digest is required before use.

The release file must be an absolute canonical non-symlink path, at most 1 MiB, owned by the service user with no group/other permissions. Runtime verifies its canonical digest against the separate approved value. It verifies the complete running source inventory before constructing connections. Streamlit `[auth]` must have exactly the matching redirect_uri, client_id and server_metadata_url plus nonempty client_secret and a cookie_secret of at least 32 characters. Named-provider overrides and unreviewed extra auth options are blocked. Sign-in remains the server-owned Streamlit OIDC session; this module does not authenticate uploaded tokens or infer identities from emails.

Role DSNs are held only in server secrets: `CAMPAIGNIQ_ACCOUNTS_INPUT_DSN`, `CAMPAIGNIQ_ACCOUNTS_PUBLICATION_DSN`, and `CAMPAIGNIQ_ACCOUNTS_PREFERENCES_DSN`. Existing target/TLS/routing guards validate every DSN before any database connection. Startup then opens a separate read-only repeatable transaction under each actual role, validates its exact effective permission profile, the complete versioned schema and versions 1–4 ledger, current audited directory and trusted legacy mapping. Different directory snapshots cause a stop/retry. No startup operation initializes storage, migrates, bootstraps, grants privileges, repairs corrupt sources, or writes financial/preference rows. Failures show generic errors without DSNs, subjects, credentials or database exception text. The account UI renders only after all preflight checks pass.

The committed application rehearsal now calls these startup checks against all three actual restricted roles on its disposable local clone. It retains the existing independent original-restore verification and identity-checked clone/role cleanup. Its check count becomes 24. The bundled worker import check includes the startup/configuration/packet modules and runs with `-I -S` without installed site packages.

After committing the tested increment, prepare the offline review packet with:

```
PYTHONPATH=src python -m campaigniq.account_release_packet --repo "$HOME/CampaignIQ-release" --development-only
```

This command requires the clean reviewed feature checkout and rejects Render. It creates a private new records directory containing the exact committed Python source inventory, activation/recovery procedures and a readiness report. It makes no database or network connection, embeds no credentials or inferred ownership, never overwrites an existing packet, and always reports activation_ready=false. A fresh production capture, independently verified backup, complete ownership and preference review, exact schema/bootstrap/grant plans, private release configuration, real owner/report verification and explicit production authorization are still required. No production migration/apply command is introduced in this increment.

Recovery is code/configuration rollback while preserving account tables, audits and all subsequent user records. Restoring an older whole database or dropping the account schema is not an acceptable routine rollback. The offline packet preserves that distinction and does not replace the historical publication recovery tooling.
