# One snapshot for saved-month listing and display

After consolidated display reads, Data still used seven input-gateway connection setups and two continuation initializations per visit. The draft list and selected-draft display each opened their own guarded read transaction. This checkpoint combines those two reads, leaving overview, retained-history UI and explicit actions independent.

DeploymentMonthlyApplication.draft_screen opens one fresh authorized READ ONLY snapshot, lists only the current account's drafts, selects the saved preferred ID (or the first listed draft on initial entry), checks that selection belongs to this list, verifies the selected draft's original checksums and revision, and builds the same publication/inventory/no-trading display state as draft_display. Published result replay still executes. Only detached draft records and display values are returned, and the gateway expires the session. The existing draft_display API keeps its displayed-revision contract and uses the same internal display helper.

The UI reads its account-scoped saved-month preference before the combined call. Month changes trigger another complete request and read. If the widget and returned selection differ, the page reruns before using the display. An unavailable preferred draft is rejected instead of selecting another month silently. Reload saved months explicitly clears only that display preference, then performs a fresh guarded read; it never removes or resets draft data. Local and older service fallbacks retain their separate-read behavior.

No selected-draft display data grants publication readiness or authority. Saves, explicit reviews, confirmations, recovery, results and publication keep their own fresh access/transaction/revision checks. No connection is held open across widget rendering or a user action, and no cross-request cache is introduced. A fixed draft_screen operation timing includes listing plus display; comparing it directly with a metadata-only timer would be misleading.

Tests cover one transaction and selected-only original checking, initial and explicit selection, empty listings, foreign actor/account/draft rejection, invalid preference types, revision mismatch, next-request freshness, actual Streamlit month changes on published and unpublished pages, and preference-only reload. The disposable PostgreSQL rehearsal adds restricted-role foreign-selection/readonly-SQL tests and published canonical-generation/inventory parity. The actual connection count and speed benefit require a fresh production timing capture after exact release review and deployment.
