# Consolidated Data draft display snapshot

Production phase timings showed ten input-gateway connection setups on Data, totaling about 2.46–3.14 seconds per visit. This checkpoint combines selected-draft publication status, saved-document metadata/protection and no-trading status in one fresh authorized READ ONLY transaction. Overview, draft selection and explicit actions remain separate; this does not make the entire page one transaction.

DeploymentMonthlyApplication.draft_display validates the displayed integer source revision, opens the existing guarded gateway transaction, checks all original checksums with _lock, checks the exact deployment publication receipt, and fully replays published results when present. It then builds the same recovery inventory metadata/protection and existing no-trading receipt-presence status for an unpublished draft. Session checks run before return and the gateway expires the handle. Only detached display data is returned. No browser/session-state cache or raw database handle is introduced.

The deployment UI consumes this snapshot for publication display, workflow default and document listing. The recovery renderer accepts an optional inventory for this presentation only; its review and apply operations still compute fresh server-side plans. All save, confirmation, review, recovery, result and publication calls keep their original independent authorization/transactions and revision checks. No display result grants permission or publication readiness.

The deployment overview already enters the exact same role/schema-verified input gateway as storage_ready (which merely called overview again). When the new display API is available, that redundant readiness call is omitted. Local/older services retain their existing readiness and separate-read paths. An overview schema/role failure still prevents the page from rendering; there is no initialization fallback. Explicit operations still recheck current access.

A fixed draft_display operation label replaces the separate saved_documents operation timing on this UI path. It includes publication replay and inventory/status work, so its duration must not be compared directly with the old metadata-only timer. No identifiers, document names, arguments or financial values are added to telemetry.

Tests cover one fresh transaction per display, exact source revision, foreign actor/account rejection, published receipt replay failure, confirmation status, detached fresh metadata on another request, session expiration and UI avoidance of duplicate reads. The disposable PostgreSQL rehearsal adds restricted-role foreign/stale/readonly-failure checks and published canonical-result/inventory parity with every database row unchanged. The full suite and exact candidate release review are required before deployment. The actual Data connection count and latency benefit must be verified from a fresh in-app capture; no speedup is claimed from synthetic tests alone.
