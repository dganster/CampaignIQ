# Transaction-local snapshot binding reuse

The first production timing capture showed warm report snapshot preparation around 2.8–3.9 seconds, with startup checks adding 0.7–0.8 seconds. This checkpoint removes redundant directory loads in the current financial snapshot and adds finer stages; no production latency improvement is claimed before measurement.

_open_session already authorizes the actor and account against a directory loaded on the financial connection. After proving transaction_read_only=on and transaction_isolation=repeatable read, retain that exact directory on this session using the existing _known_directory_snapshot mechanism. Writable or other transaction modes never receive this seed. DeploymentMonthlyInputs._known still checks session expiry, SQL failure and transaction mode before every reuse. Another session loads a fresh directory. The outer directory SHARE guard, actor/account authorization, schema and role checks remain.

The deployment dashboard now obtains bindings for retained statement income and trade-history evidence through _known rather than reloading the directory in those paths. All original checksum, publication receipt, result replay, income and history verification still executes each visit. There is no cross-request report, authorization or financial-result cache, schema update, or grant change.

New allowlisted stages separate snapshot_current_result_verification, snapshot_retained_income, snapshot_history_verification, and snapshot_retained_result_verification. They appear in existing automatic statistics and sanitized downloads without new identifiers or financial fields. These stages nest inside existing page/transaction work; durations overlap and cannot be summed. Retained result verification also covers continuation setup on the Data route. Some work remains outside these stages; this is not complete SQL-level instrumentation.

Tests verify same-connection authorization occurs before reuse, a subsequent session observes changed bindings, writable/read-committed/non-readonly modes do not reuse, expired/failed/idle sessions cannot obtain seeded bindings, and the new names reach timing output. Existing snapshot/document reuse, dashboard isolation/revocation and timing tests are retained. Run the full local suite and disposable PostgreSQL rehearsal, then an exact read-only production candidate review before deployment. Compare measured latency after release before choosing the next optimization.
