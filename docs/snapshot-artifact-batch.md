# Bounded transaction-local artifact batch reads

The warm account snapshot still took about 2.6–3.7 seconds after the first binding-read reduction. Continuation validated namespace keys once, but fetched each new artifact's text with a separate SQL round trip. This checkpoint batches that exact namespace's bytes within the current authorized read-only repeatable transaction.

DeploymentDataSession now uses _SnapshotArtifacts. Before loading contents it queries row count and total UTF-8 key/content bytes for the exact namespace. At most 512 rows and 32 MiB of content/key bytes are retained. If either limit is exceeded, the session uses existing individual reads, remembering only that batching was declined. The count/size and actual batch must match; a mismatch is rejected without adopting bytes. Empty namespaces are valid snapshots. This bounds retained payload size, not total Python allocator overhead.

Each read_text, exists and list_keys checks expiry, transaction error state and the existing read-only/repeatable proof before using retained bytes. Writable/read-committed/non-readonly modes retain individual reads. Fresh sessions fetch fresh data; a namespace change discards the prior batch. Missing keys still raise FileNotFoundError and key validation remains. Read-only writes and initialization remain prohibited. Continuation overlap, receipt, original checksum, published result, broker identity, income and source verification still run against the exact same transaction's bytes.

This is not a cross-request financial-result or authorization cache. No schema, grants, credentials, runtime settings or financial arithmetic changes are introduced. The outer directory authorization guard remains. A larger first fetch can cost more for a tiny operation, so the exact production candidate profile and post-release measurements must determine whether the tradeoff helps. No production speedup is claimed before measurement.

Tests cover one exact batch across repeated reads, filtering/missing/unicode behavior, session expiration and SQL failure, write and isolation-mode fallback, byte/entry limits, new sessions and namespace isolation, conflicting inventories, and write/key rejection. Existing snapshot, document, binding and dashboard tests remain. The full suite and disposable PostgreSQL rehearsal are required before the read-only production release review.
